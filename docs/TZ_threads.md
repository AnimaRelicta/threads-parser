# ТЗ: доработка threads-parser — сбор веток, классификация профилей LLM

Редакция 2 (исправлена терминология и фактические ошибки первой версии, см. раздел 10).

## 1. Термины

Три уровня иерархии, дальше в ТЗ слова используются только в этом смысле:

```
Профиль  ->  ветки  ->  посты
(аккаунт)    (ветка 1, ветка 2, ... ветка N)    (посты под веткой 1, под веткой 2, ...)
```

| Термин ТЗ | Что это | Где в коде и БД (имена исторические, не переименовываются) |
| --- | --- | --- |
| **Профиль** | аккаунт Threads, например `olx_vetka_astana` | `profiles`, `profile_anchors`, `profile_runs`, `scrape/profile.py` |
| **Ветка** | запись верхнего уровня в ленте профиля, под которой идёт обсуждение | таблица `posts` (`first_seen_via='profile'`), `shortcode`, лента `scrape/feed.py`, `FeedIndex` |
| **Пост** | ответ внутри ветки (под веткой, на любой глубине) | таблица `comments`, `scrape/comments.py`, `children.py` |

Профиль **не** ветка. В редакции 1 эти понятия были смешаны, из-за этого «сбор веток» превращался в «сбор профилей». Названия таблиц `posts` и `comments` остаются как есть: переименование ломает рабочие базы и не нужно. В коде и README рядом с ними ставится пометка «ветка» / «пост под веткой». В новых модулях и колонках слово `thread` означает ветку, `reply` пост под веткой.

## 2. Контекст

Репозиторий `threads-parser` собирает данные Threads через Playwright и пишет в Postgres (схема `threads`). Сейчас умеет:

- обойти список профилей (`data/threads_profiles.txt`, позиционный аргумент, `--file`) и для каждого собрать ветки за период (`--since`, `--limit`), открыв каждую ветку, скачав медиа и (с `--comments`) посты под веткой деревом;
- искать ветки по ключевым словам в выдаче Threads (`search.py`, `serp/*`).

Чего нет:

- быстрого режима «только список веток профиля за период» без открытия каждой ветки;
- парсинга постов под веткой по заранее собранному списку веток;
- поиска новых профилей-кандидатов по авторам постов под ветками и по авторам найденных веток;
- категорий профилей и обращения к LLM.

Архитектура: CLI `run.py` (профили), `search.py`, `accounts.py`, сводный `cli.py`, `dbadmin.py`. Пакеты `core/` <- `db/` <- `registry/`/`browser/` <- `scrape/` <- `serp/` <- CLI (импорты только вниз). Миграции `db/migrations/NNN_*.sql`; `001_init.sql` не править: она применена на рабочих БД.

## 4. Шаг 2. Быстрый сбор веток по профилю

Цель: по имени профиля пробежать ленту и сохранить в БД все ветки за выбранный период, **не открывая сами ветки**. Работает как существующий обход профиля в `run_profile()` (тот же вход в профиль, `--since`, `--limit`, закреплённые ветки, остановка по старым), но без `scrape_post()`, медиа и постов под веткой.

### 4.1. Запуск

```
uv run scripts/cli.py parse olx_vetka_astana --threads-only --since 7d
uv run scripts/cli.py parse --file data/threads_profiles.txt --threads-only --since 1m
```

Новый флаг `--threads-only` в `run.py`. Общие флаги (`--since`, `--limit`, `--accounts`, `--workers`, `--headless`, `--delay`, `--profile-delay`, `--full`, `--stop-after`) работают как обычно. Флаги про содержимое ветки (`--comments`, `--depth`, `--max-comments`, `--with-videos`, `--recheck-days`, `--full-rescan`, `--no-block`) в этом режиме не используются; при явной передаче печатается предупреждение. Очередь профилей, аккаунты, воркеры, повторы при 429 и авторизация берутся из `scrape/dispatch.py` без изменений.

### 4.2. Что собирается

Только из JSON ленты (то, что `FeedIndex` и так получает при прокрутке), без перехода на страницу ветки:

| Поле | Источник в JSON ленты | Колонка `posts` |
| --- | --- | --- |
| `code` | `code` | `code` |
| ссылка | `/@{username}/post/{code}` | `url` |
| автор | `user.username`, `user.pk` | `author_username`, `author_user_id` |
| текст | caption | `text` |
| дата | `taken_at` | `date_utc` |
| лайки, репосты, цитаты | счётчики объекта | `likes`, `reposts`, `quotes` |
| число ответов | `text_post_app_info.direct_reply_count` | `reply_count` |
| есть видео | `is_video_obj()` | ветка с видео **сохраняется** (текст у неё есть), файлы не качаются |

Какие поля лента реально отдаёт, подтверждается в начале шага 2 на живом профиле. Чего в ленте нет, остаётся `NULL`; ветка из-за этого не открывается.

`FeedIndex._add_doc()` в `scrape/harvest.py` расширяется: сейчас хранит только `ts`, `replies`, `video`; добавляются `text`, `likes`, `reposts`, `quotes`, `author`, `author_id`. Прежние ключи и их потребители (`profile.py`, `is_pinned`) не меняются.

### 4.3. Обход ленты и границы периода

- Вход в профиль, проверка `/login`, 404, 429, сбор `og_*` как в `run_profile()`; общий код выносится в функцию, не дублируется.
- Ленту листает `iter_post_links()`. Правило «старше `cutoff`» то же, что в профильном проходе: `ts < cutoff` и ветка не закреплена (`is_pinned`); остановка после `OLD_STREAK_STOP` подряд старых. Закреплённые ветки берутся независимо от `--since`.
- `--limit N` в этом режиме ограничивает число веток на профиль (0 = все за период).
- Остановка по известным: без `--full` обход прекращается после `--stop-after` подряд веток, которые уже есть в `posts` для этого профиля. **Якорь `profile_anchors` в этом режиме не читается и не пишется**: он означает «профиль разобран полностью, с постами под ветками», а здесь ветки не разбираются.
- Нужна только вкладка ленты; вкладка веток и блокировка ресурсов не используются.

### 4.4. Запись в БД

- Ветка пишется в `posts` upsert'ом по `code`: `first_seen_via='profile'`, `profile_id` профиля, `last_refreshed_at = NULL`, `visited_reply_count = NULL`. По `last_refreshed_at IS NULL` позже отличаются ветки без разобранных постов (в существующем коде `save_post()` по этому же признаку отличает полностью собранные ветки от найденных поиском).
- Если ветка уже собрана полностью (`last_refreshed_at IS NOT NULL`), быстрый режим обновляет только счётчики (`likes`, `reply_count`, `reposts`, `quotes`); `text`, `date_utc`, `comments`, `media` не трогает.
- Фильтр «олх» (`classify()` из `core/textfilter.py`) применяется к тексту ветки как при обычном сохранении, чтобы `filter_status` не оставался значением по умолчанию `rejected`.
- Запись батчем (`executemany`) на каждую прокрутку, не по одной ветке.
- Новая функция в `db/posts.py` (например `save_threads_light(conn, profile_id, username, items)`) и метод в `ProfileStore`; `save_post()` не меняется.

### 4.5. Учёт запуска

- Через существующие `start_run(conn, 'profiles', settings)` / `finalize_run()`; в `settings` добавляется `{"mode": "threads"}`.
- Строка `profile_runs` на профиль с `mode='threads'` (колонка без `CHECK`, миграция не нужна). Счётчики: `posts_new` = новых веток, `posts_unchanged` = уже известных, `posts_skipped_old` = старых, `posts_in_period` = веток за период, `posts_newest` = дата самой свежей. Колонки названы историческим словом `posts`, но в этом режиме считают ветки; пометка в README.
- Итог на профиль в консоли: сколько веток за период, сколько новых, дата самой свежей.

### 4.6. Миграция `002_threads_light.sql`

Минимальная, индекс под выборку «ветки профиля без разобранных постов»:

```sql
CREATE INDEX IF NOT EXISTS posts_profile_pending
    ON threads.posts (profile_id, date_utc DESC)
    WHERE last_refreshed_at IS NULL;
```

## 5. Шаг 3. Источник профилей и парсинг постов под собранными ветками

### 5.1. Выбор профилей: `--source`

Новый флаг `run.py --source` формирует список профилей перед диспетчером; дальше всё как сейчас. Работает и с `--threads-only`, и с обычным режимом.

| Значение | Какие профили |
| --- | --- |
| `all` | все `profiles` с `is_target = true` (по умолчанию, если не указан ни профиль, ни `--file`; файл остаётся запасным вариантом) |
| `<ник>[,<ник>...]` | конкретные профили (как позиционный аргумент) |
| `search` | профили с `discovered_via='search'`: авторы веток, найденных `search.py` |
| `authors` | профили с `discovered_via='author'`: авторы постов под ветками (шаг 4) |
| `new` | профили, у которых нет ни одной собранной ветки |

Выбор одной функцией `list_targets(conn, source, review_status=None) -> list[str]` в `db/profiles.py`; её же используют `search.py` и `dbadmin.py` для отчётов. Колонка `discovered_via` появляется в шаге 4; до него `search` и `authors` недоступны, `all`, `new` и список ников работают сразу.

### 5.2. Парсинг постов под уже собранными ветками

```
uv run scripts/cli.py parse olx_vetka_astana --fill-threads --since 7d --comments --depth 3
```

- Флаг `--fill-threads`: вместо обхода ленты берёт ветки профиля из `posts` (`last_refreshed_at IS NULL`, `date_utc >= cutoff`) и для каждой вызывает существующие `scrape_post()` / `refresh_comments()`. Флаги глубины и комментариев те же.
- Закреплённость не вычисляется: период уже применён при сборе веток.
- После разбора ветка получает `last_refreshed_at` обычным путём через `save_post()`.
- Якорь в этом режиме не пишется: полнота прохода по ленте им не подтверждается.
- Смысл двух шагов: быстрый режим стоит одного прохода по ленте на профиль, а дорогой разбор можно запускать позже и выборочно (`--source`, `--since`).

### 5.3. Критерии приёмки шага 3

- [ ] `--source all|<ники>|new` отбирает профили, не меняя поведение якоря и `only_new`.
- [ ] `--fill-threads` разбирает только ветки без `last_refreshed_at` и за период; после прохода они получают `last_refreshed_at`.
- [ ] Повторный `--fill-threads` ничего не открывает.

## 6. Шаг 4. Новые профили по авторам

После разбора веток в `comments.author` (посты под ветками) и `posts.author_username` (ветки из поиска) накапливаются ники, которых нет в `profiles`. Это кандидаты на новые профили.

Процедура `db/discovery.py` (флаг `run.py --discover-authors` или подкоманда):

1. Собрать уникальные ники из `comments.author` и из `posts.author_username` с `profile_id IS NULL` за период `--since`.
2. Исключить тех, кто уже есть в `profiles` (по `lower(username)`), и автора, который пишет под собственной веткой.
3. Вставить в `profiles`: `discovered_via` (`author` для авторов постов под ветками, `search` для авторов веток из поиска), `discovered_from_profile_id`, `is_target = true`, `review_status = 'pending_review'`.
4. По желанию: `mentions_count` и код первой ветки/поста, где автор встретился.

Миграция `003_discovery.sql`, колонки `profiles`: `discovered_via TEXT NOT NULL DEFAULT 'seed_list' CHECK (discovered_via IN ('seed_list','search','author'))`, `discovered_from_profile_id BIGINT REFERENCES profiles(id)`, `review_status TEXT NOT NULL DEFAULT 'new' CHECK (review_status IN ('new','pending_review','reviewed','review_failed'))`. `review_status` описывает **профиль**, не ветку.

Критерии: авторы попадают в `profiles` без дублей по `lower(username)`; повторный запуск ничего не добавляет; авторы собственных веток не попадают.

## 7. Шаг 5. Аудит схемы и единый учёт запусков

`001_init.sql` не править; всё миграцией `004_*.sql`. Результат проверки по коду на момент редакции 2:

| Кандидат | Результат проверки | Решение |
| --- | --- | --- |
| `custom_topics` | в коде не используется, только создаётся в `001_init.sql` | удалить |
| `skipped_posts` | **используется**: `db/posts.py` (`load_skipped`, `mark_skipped`) и `scrape/profile.py` (профильный проход по ней пропускает уже виденные старые и видео-ветки без повторного открытия и считает серию известных для якоря) | **оставить**; счётчики в `profile_runs` её не заменяют; в таблице ветки, а не посты под ветками, оставить комментарий |
| `search_jobs` и `runs` | не дублируют друг друга: очередь задач и сводка запуска; `serp/runner.py` уже вызывает `start_run('search')` и `finalize_run()` | оставить как есть |
| `categories` (шаг 6) | новая сущность | один справочник, без второго enum на тот же список |

Единый учёт: расширить `runs.kind` до `CHECK (kind IN ('profiles','search','discover','classify'))` и использовать `start_run()`/`finalize_run()` для `discover` и `classify`. Быстрый сбор веток остаётся `kind='profiles'` с `settings.mode='threads'`. Итоги по профилям в `profile_runs` (`mode='discover'`/`'classify'`) либо в `runs.settings`/`runs.error`; отдельные таблицы только если нужны построчные итоги, которых `profile_runs` не покрывает.

Отчёты в `db/stats.py` через `register(Report(...))`: очередь на проверку, распределение по категориям, среднее время классификации профиля, сколько веток собрано быстрым режимом и сколько из них ещё без постов.

## 8. Шаг 6. Категории профилей и классификация LLM

### 8.1. Категории

Справочник `categories` (миграция `005_categories.sql`, по стилю как `topics`: `id SMALLINT PRIMARY KEY`, `code TEXT UNIQUE`, `name_ru TEXT`, `description TEXT`, `is_active BOOLEAN DEFAULT true`). Набор по умолчанию, 7 строк `INSERT`ом, редактируется в БД:

| код | название |
| --- | --- |
| `vitrina` | Витрина |
| `baraholka` | Барахолка |
| `reseller` | Перекупщик |
| `news` | Новости |
| `house_chat` | Домовой чат |
| `services` | Услуги |
| `other` | Прочее |

Категория относится к **профилю**: `profiles.category_id SMALLINT REFERENCES categories(id)`, `category_raw JSONB`, `category_model TEXT`, `category_prompt_version SMALLINT`. Классификация отдельных веток (`posts.category_id`) в обязательную часть не входит.

### 8.2. Пакет `scripts/classify/`

Модуль на задачу, без браузера и Playwright, импорты вниз (`core`, `db`):

- `client.py`: HTTP-клиент к proxy API модели, таймаут, повторы при 429/5xx. В `pyproject.toml` сейчас только `asyncpg` и `playwright`, `httpx` в проекте **нет**: в начале шага решить, добавить `httpx` (и обновить `uv.lock`) или обойтись стандартной библиотекой.
- `prompts.py`: системный промпт с категориями из `categories`, ответ строго JSON `{"category": "vitrina", "confidence": 0.8, "reason": "..."}`.
- `classifier.py`: `classify_profile(profile, sample_threads) -> ClassifyResult`. Контекст: `og_title`, `og_description` и N последних **веток** профиля из `posts`; посты под ветками в контекст не берутся. Неизвестный код или невалидный JSON дают `other` с пометкой об ошибке, не исключение.
- `runner.py`: воркер по профилям с `review_status='pending_review'`, `asyncio.Semaphore`, запись `category_id` и `review_status` (`reviewed` / `review_failed`), запуск в `runs` (`kind='classify'`).
- CLI: `uv run scripts/cli.py classify [--source pending_review] --limit N [--workers N] [--recheck]`, строка в `COMMANDS` в `cli.py`; `--limit` обязателен.

`.env.example`: блок `--- LLM-классификация ---`: `LLM_PROXY_URL`, `LLM_PROXY_API_KEY`, `LLM_MODEL`, `LLM_TIMEOUT_SEC`, `LLM_MAX_RETRIES`, `LLM_WORKERS`, `LLM_SAMPLE_THREADS`. Настройки в `config.py` по паттерну `Settings`; ключ и URL только в `scripts/.env` (уже в `.gitignore`).

### 8.3. Надёжность

- Переходы `review_status`: `new -> pending_review -> reviewed | review_failed`, при `--recheck` `reviewed -> pending_review`; невалидные запрещаются на уровне БД.
- Выборка партии `SELECT ... FOR UPDATE SKIP LOCKED`, чтобы воркеры не брали один профиль дважды. В текущем коде `SKIP LOCKED` нигде не используется, это новая практика проекта.
- Ошибки proxy API (таймаут, 429, невалидный JSON) не роняют процесс: профиль получает `review_failed`, цикл продолжается. 401/403 останавливает запуск целиком.
- Расход запросов к LLM за период виден в отчёте `db/stats.py`.

## 10. Что исправлено относительно редакции 1

1. **Терминология.** «Ветка = профиль» заменено на иерархию профиль -> ветки -> посты под веткой (раздел 1); затронуты все задачи.
2. **Задача 1.** Была «завести профиль в БД без парсинга», стала «быстро собрать ветки профиля за период из ленты, не открывая их» (раздел 4).
3. **Задача 2.** `--source` выбирает профили; добавлен отдельный режим разбора постов под уже собранными ветками (`--fill-threads`).
4. **Задача 3.** Кандидаты в новые профили берутся из авторов постов под ветками и веток из поиска; `review_status` и `discovered_via` относятся к профилю.
